# TimeFit 모바일 앱 UI/UX 설계 기획

작성일: 2026-09-30  
문서 상태: UI/UX 구현 기준안 v1.0  
선행 문서: `128-mobile-app-product-planning-design-2026-09-30.md`, `129-mobile-app-phase2-role-based-product-design-2026-09-30.md`  
디자인 방향: Toss-inspired, TimeFit-native

## 1. 디자인 결론

TimeFit 앱은 토스의 화면을 복제하지 않는다. 토스가 보여주는 `쉬운 문장`, `분명한 정보 위계`, `한 번에 하나의 주요 행동`, `일관된 컴포넌트`, `접근성까지 포함한 완성도`를 참고해 TimeFit의 근무·승인·증빙 업무에 맞게 재설계한다.

디자인 콘셉트는 **Calm Shift**다.

- Calm: 오류와 마감이 많은 업무에서도 불안을 과장하지 않는다.
- Clear: 지금 상태와 다음 행동을 한눈에 구분한다.
- Quick: 출퇴근 10초, 승인 30초, 긴급 스케줄 수정 1분을 목표로 한다.
- Trustworthy: 금액·시간·승인 결과에는 기준 시각과 근거를 함께 보여준다.

### 화면 기본 공식

```text
가치 또는 현재 결론
→ 필요한 근거 1~3개
→ 지금 할 행동 1개
→ 상세 정보는 다음 화면
```

예:

```text
오늘은 9시에 근무해요
성수점 · 오픈 근무 · 09:00–18:00
[QR 출근하기]
```

## 2. 토스에서 참고할 원칙

### 2.1 Value first

사용자에게 입력이나 권한을 먼저 요구하지 않고, 그 행동으로 얻게 될 가치를 먼저 보여준다.

- 나쁜 예: `카메라 권한을 허용해 주세요.`
- TimeFit 문구: `매장 QR을 스캔하면 출근이 바로 기록돼요.` → `카메라 사용하기`
- 나쁜 예: `가능시간을 제출하세요.`
- TimeFit 문구: `가능한 시간을 알려주면 다음 주 근무를 더 정확하게 배정할 수 있어요.`

토스가 공개한 `Value first, Cost later` 원칙을 TimeFit의 권한 요청, 다단계 입력, 민감정보 재인증에 적용한다.

### 2.2 Easy to answer

질문의 범위를 좁히고 사용자가 기억하거나 해석해야 할 일을 줄인다.

- 휴가 신청은 유형 → 날짜 → 확인 순으로 한 단계씩 묻는다.
- 교대 요청은 가능한 대상만 보여준다.
- 영수증 수정 요청은 문제가 있는 필드로 바로 이동한다.
- 승인 화면은 원본과 변경값을 나란히 보여주고 `승인/반려` 판단만 남긴다.

### 2.3 패턴화와 예외 대응

같은 컴포넌트가 긴 문장, 큰 글자, 다크모드, 화면 읽기, 폴드폰에서도 같은 의미를 유지해야 한다. 토스 디자인 시스템의 공개 사례처럼 일반 상태뿐 아니라 실제 사용 변형을 컴포넌트 단계에서 정의한다.

### 2.4 TimeFit에서 그대로 가져오지 않을 것

- 금융 소비자 앱의 넓은 여백을 고밀도 관리자 업무에 그대로 적용하지 않는다.
- 모든 정보를 큰 카드로 만들지 않는다.
- 과도한 3D 그래픽·일러스트레이션으로 업무 상태를 가리지 않는다.
- 파란색을 모든 배경에 사용하지 않는다.
- 친근한 문구가 책임과 결과를 흐리게 하지 않도록 한다.
- 출퇴근·급여·승인 같은 중요한 행동에 장식적 모션을 사용하지 않는다.

## 3. 브랜드 시각 방향

### 3.1 TimeFit만의 시각적 특징

토스와 구분되는 TimeFit의 핵심 시각 언어는 `시간`, `근무 상태`, `현장 소속`이다.

- 시간: 시작·종료 시각과 남은 시간을 굵고 정렬된 숫자로 표현
- 상태: 예정, 근무 중, 확인 필요, 완료를 동일한 상태 체계로 표현
- 소속: 사업장·부서·역할을 작은 텍스트와 라벨로 명확히 구분
- 흐름: 요청이 누구에게 넘어갔고 다음에 무엇이 일어나는지 단계로 표현

### 3.2 로고·브랜드 사용

- 앱 아이콘은 `T`와 시간 진행을 암시하는 간결한 형태를 사용한다.
- 화면 상단에 로고를 반복하지 않고 로그인·빈 상태·앱 정보에서만 사용한다.
- 브랜드 블루는 주요 행동과 선택 상태에 집중한다.
- 브랜드 이름보다 현재 사업장과 사용자 역할을 먼저 보여준다.

### 4.2 타이포그래피

권장 폰트: Pretendard Variable, 시스템 폰트 폴백

| 스타일 | 크기/행간 | 굵기 | 사용 |
|---|---|---|---|
| Display | 32/42 | 700 | 홈의 한 문장 결론 |
| Title 1 | 28/38 | 700 | 화면 제목 |
| Title 2 | 22/30 | 700 | 섹션 결론 |
| Headline | 18/26 | 700 | 카드·목록 제목 |
| Body 1 | 16/24 | 500 | 주요 본문·버튼 |
| Body 2 | 15/22 | 400~500 | 일반 본문 |
| Caption | 13/19 | 500 | 기준 시각·보조 정보 |

규칙:

- 한 화면에서 700 굵기는 결론, 금액, 주요 상태에만 사용한다.
- 시간·금액·인원에는 tabular number를 적용한다.
- 음수 기호와 단위가 줄바꿈으로 분리되지 않게 한다.
- 시스템 글자 크기 200%에서도 주요 행동이 잘리지 않게 한다.

### 4.3 간격과 레이아웃

- 기본 간격 체계: 4, 8, 12, 16, 20, 24, 32, 40
- 모바일 좌우 여백: 20px, 360px 이하에서 16px
- 섹션 간격: 32px
- 관련 요소 간격: 8~12px
- 최소 터치 영역: 48×48dp
- 하단 고정 CTA 높이: 56px
- 상단 앱 바: 56px + 안전영역
- 하단 내비게이션: 64px + 안전영역

### 4.4 모서리와 그림자

| 요소 | 반경 |
|---|---:|
| 버튼·입력 | 12px |
| 작은 상태 표면 | 10px |
| 카드 | 18px |
| 바텀시트 | 상단 24px |
| 전체 화면 모달 | 기기 규칙 따름 |

- 카드 기본 그림자는 사용하지 않는다.
- 떠 있는 바텀시트, 메뉴, 토스트에만 낮은 그림자를 사용한다.
- 테두리와 배경 차이만으로 구조를 이해할 수 있으면 그림자를 제거한다.

## 5. 내비게이션 설계

### 5.1 직원

```text
홈 / 스케줄 / 출퇴근 / 요청 / 전체
```

- 홈은 오늘의 행동과 대응이 필요한 항목만 보여준다.
- 스케줄은 읽기와 변경 확인 중심이다.
- 출퇴근은 QR 행동과 기록 근거를 제공한다.
- 요청은 휴가·근태 수정·교대·영수증을 한 곳에서 추적한다.
- 전체에는 급여명세, 공지, 알림, 설정을 둔다.

### 5.2 매니저

```text
홈 / 직원 / 스케줄 / 승인 / 전체
```

- 승인 배지는 미처리 건수가 아니라 오늘 조치가 필요한 건수를 우선 표시한다.
- 재무 권한이 없는 매니저에게 지출·급여 메뉴를 노출하지 않는다.

### 5.3 총관리자

```text
홈 / 운영 / 승인 / 요약 / 전체
```

- `요약`은 데이터 완결성이 확인된 사업장에만 표시한다.
- 설정, 급여 마감, 월 결산은 `웹 관리자에서 계속`으로 연결한다.

### 5.4 사업장·역할 전환

- 앱 바의 사업장명을 누르면 바텀시트를 연다.
- 각 행에 사업장명, 활성 역할, 미처리 중요 업무를 표시한다.
- 역할 전환은 메뉴와 캐시를 교체하고 화면 상단에 짧게 결과를 알린다.
- 입력 중에는 전환 전에 임시 저장 또는 폐기를 확인한다.

## 6. 홈 화면 설계

### 6.1 직원 홈

#### 상단

- 인사말보다 오늘의 근무 결론을 먼저 표시한다.
- 사업장과 알림은 앱 바에 둔다.
- 날짜는 결론 위의 작은 보조 정보로 사용한다.

#### 주요 상태

```text
오늘은 9시에 근무해요
성수점 · 오픈 근무 · 09:00–18:00
[QR 출근하기]
```

상태별 변화:

| 상태 | 제목 | 주 행동 |
|---|---|---|
| 근무 전 | 오늘은 9시에 근무해요 | QR 출근하기 |
| 근무 중 | 지금 근무 중이에요 | 근무시간 보기 |
| 퇴근 가능 | 퇴근 기록을 남겨주세요 | QR 퇴근하기 |
| 휴무 | 오늘은 쉬는 날이에요 | 다음 근무 보기 |
| 변경 확인 | 근무 시간이 바뀌었어요 | 변경 확인하기 |
| 예외 | 예정된 근무가 없어요 | 예외 출근 안내 |

#### 홈 정보량

- 주요 행동 1개
- 대응할 일 최대 3개
- 빠른 행동 최대 3개
- 이번 주 요약 1개
- 다음 근무 1개

나머지는 각 상세 화면으로 이동한다.

### 6.2 매니저 홈

```text
오늘 먼저 볼 일이 2개 있어요
지각 1명 · 휴가 승인 1건
[승인함 열기]
```

구성:

1. 운영 결론
2. 우선 작업 큐 최대 3행
3. 직원 현황 숫자 4개
4. 오늘 인원과 부족 구간
5. 미확인 스케줄 변경

작업 행에는 상태 아이콘, 행동형 제목, 영향, 기한을 표시한다. 각 작업을 별도 카드로 만들지 않는다.

### 6.3 총관리자 홈

```text
운영은 대체로 정상이에요
급여 마감 전 근태 2건만 확인해 주세요
[확인할 일 보기]
```

재무 요약:

- 완료 매출
- 확정 지출
- 예상 인건비
- 잠정 순익

같은 기간과 같은 데이터 기준 시각을 사용한다. 정보가 불완전하면 숫자 대신 `일부 데이터 갱신 중`과 마지막 정상 시각을 표시한다.

## 7. 핵심 화면별 UX

### 7.1 QR 출퇴근

- 진입 즉시 카메라를 열기 전에 한 줄 가치를 보여준다.
- 스캔 영역은 화면 중앙의 하나의 프레임으로 제한한다.
- 손전등, 카메라 권한 안내, 직접 요청을 보조 행동으로 제공한다.
- 인식 후 별도 긴 확인 폼 없이 사업장과 행동을 짧게 확인한다.
- 성공 화면은 시각, 사업장, 다음 행동을 표시하고 자동으로 홈에 반영한다.
- 실패는 `인식 실패`가 아니라 만료, 다른 사업장, 네트워크, 중복 등 원인을 구분한다.

### 7.2 스케줄

- 기본은 주간 리스트다. 월간 달력은 날짜 선택과 상태 요약에 사용한다.
- 날짜, 시간, 근무지, 근무 유형의 읽기 순서를 고정한다.
- 변경된 일정은 이전 값을 취소선으로 표시하기보다 `이전/변경` 두 행으로 명확히 비교한다.
- 오늘, 휴무, 휴가, 미확인은 색 외에 라벨을 함께 사용한다.
- 직원 가능시간과 실제 배정을 같은 색으로 혼동하지 않는다.

### 7.3 교대·대타

- 요청 시작 시 가능한 세 가지 방식 중 정책상 허용된 것만 보여준다.
- 대상 직원 목록에는 가능한 사람만 우선 표시하고 제외 이유를 설명한다.
- 요청 완료 후 단계 타임라인으로 현재 담당자를 보여준다.
- 후보 수락과 매니저 최종 승인을 시각적으로 분리한다.
- 승인 후 두 직원의 새 일정을 한 화면에서 확인한다.

### 7.4 승인함

- 상단은 탭보다 `오늘 처리`, `마감 영향`, `전체` 필터를 우선한다.
- 목록 행은 요청 유형보다 영향과 기한을 먼저 보여준다.
- 상세는 결론 → 변경 비교 → 근거 → 이력 → 행동 순서다.
- 승인과 반려 버튼을 같은 시각적 무게로 두지 않는다. 권장 행동이 명확할 때만 승인에 높은 강조를 준다.
- 반려에는 사유 선택 후 필요한 경우 설명을 추가한다.
- 처리 후 다음 건으로 자동 이동할지 사용자 설정을 기억한다.

### 7.5 영수증

- 첫 화면은 카메라 촬영 하나를 주 행동으로 둔다.
- 화질 문제는 촬영 직후 이미지 위에 위치와 원인을 표시한다.
- OCR 결과에서는 맞는 값을 다시 입력시키지 않는다.
- 수정 요청을 받으면 잘못된 필드만 상단에 모은다.
- 원본과 수정값은 같은 화면에서 확인한다.
- `분석 완료`, `직원 제출`, `증빙 승인`, `지출 확정`을 서로 다른 상태 문구로 사용한다.

### 7.6 급여명세

- 첫 화면에는 귀속월, 지급일, 실지급액을 명확히 표시한다.
- 지급과 공제를 접을 수 있는 목록으로 구분한다.
- 전월 차이는 금액과 원인 항목을 함께 표시한다.
- 근무시간을 누르면 승인된 근태 근거로 이동한다.
- 비교가 의미 없는 경우 변화율을 억지로 보여주지 않는다.
- PDF 공유 전 민감정보 경고를 바텀시트로 제공한다.

### 7.7 공지

- 일반 공지는 읽기만, 중요 공지는 `확인했어요` 행동을 사용한다.
- 제목에 `필독`, `긴급`을 반복하지 않고 상태 라벨을 사용한다.
- 수정된 공지는 변경 부분과 새 버전을 보여준다.
- 법적 동의가 필요한 문서는 공지 확인과 분리한다.

## 8. 핵심 컴포넌트

### 8.1 Top App Bar

- 좌측: 현재 사업장과 전환 화살표
- 우측: 알림, 필요 시 프로필
- 화면 제목은 콘텐츠 영역에 배치한다.
- 스크롤 시 앱 바 배경만 불투명해지고 제목을 중복 표시하지 않는다.

### 8.2 Primary CTA

- 한 화면에 하나만 사용한다.
- 문구는 `확인`, `저장` 대신 결과가 보이게 작성한다.
  - `QR 출근하기`
  - `교대 요청 보내기`
  - `변경된 근무 게시하기`
- 로딩 중에도 버튼 폭이 바뀌지 않는다.
- 성공 후 같은 버튼을 중복 탭할 수 없게 상태를 교체한다.

### 8.3 Action Row

- 작업 목록의 기본 단위다.
- 아이콘, 행동형 제목, 영향·기한, 이동 표시로 구성한다.
- 전체 행이 눌리지만 보조 행동이 있으면 명시적 텍스트 버튼을 제공한다.
- 카드가 아닌 구분선 목록을 기본으로 한다.

### 8.4 Status Chip

- 최대 두 단어를 권장한다.
- `승인 대기`, `수정 필요`, `근무 중`, `잠정`처럼 사용자 언어를 쓴다.
- 기술 상태 `processing`, `matched`를 그대로 노출하지 않는다.

### 8.5 Bottom Sheet

적합:

- 역할·사업장 전환
- 짧은 선택 목록
- 공유 경고
- 승인 사유 선택

부적합:

- 긴 입력 폼
- 키보드와 달력이 동시에 필요한 흐름
- 여러 단계의 교대 요청

### 8.6 Empty State

- 이유 → 상태 → 가능한 행동 순서로 작성한다.
- 큰 일러스트레이션보다 작은 아이콘과 문장을 사용한다.
- 정상적인 빈 상태는 성공색이나 축하 모션을 남용하지 않는다.

### 8.7 Skeleton·Progress

- 전체 화면 스피너 대신 영역별 스켈레톤을 사용한다.
- 마지막 정상값이 있으면 유지하고 `갱신 중`을 표시한다.
- 출퇴근·승인처럼 결과가 중요한 작업은 버튼 내부 진행과 중복 방지를 사용한다.

## 9. UX Writing

### 9.1 문장 원칙

- 존댓말 `-해요`체를 기본으로 사용한다.
- 한 문장에는 하나의 정보만 담는다.
- 사용자의 잘못으로 단정하지 않는다.
- 기술 용어보다 상태와 다음 행동을 말한다.
- 불안을 자극해 클릭을 유도하지 않는다.
- `완료되었습니다`보다 `출근이 기록됐어요`처럼 결과를 구체적으로 쓴다.

### 9.2 문구 예시

| 상황 | 사용하지 않음 | 권장 |
|---|---|---|
| 네트워크 | 서버 오류가 발생했습니다 | 연결이 불안정해요. 다시 시도해 주세요. |
| 중복 출근 | 잘못된 요청입니다 | 이미 09:02에 출근이 기록됐어요. |
| 미출근 | 무단결근 1명 | 예정 시간이 지났지만 출근 기록이 없는 직원이 있어요. |
| 휴가 충돌 | 신청 불가 | 같은 날짜에 승인된 휴가가 있어요. |
| 영수증 | OCR FAILED | 금액을 읽지 못했어요. 직접 확인해 주세요. |
| 급여 | 오류 가능성 | 근태 변경 후 급여가 다시 계산되지 않았어요. |
| 권한 | 접근 거부 | 이 업무를 처리할 권한이 변경됐어요. |

## 10. 모션과 햅틱

| 상황 | 모션 | 햅틱 |
|---|---|---|
| 탭 전환 | 160ms fade/slide | 없음 |
| 버튼 눌림 | 90ms scale 0.98 | light |
| 출퇴근 성공 | 체크 220ms | success |
| 승인 완료 | 행 상태 전환 180ms | light |
| 오류 | 아이콘·문구 즉시 표시 | warning/error |
| 바텀시트 | 플랫폼 기본 감속 | 없음 |

규칙:

- 반복·루프 모션을 사용하지 않는다.
- `동작 줄이기` 설정에서는 이동을 fade로 대체한다.
- 모션이 완료 여부를 전달하는 유일한 수단이 되지 않게 한다.
- 급여·승인·출퇴근의 결과는 텍스트로 확정한다.

## 11. 접근성

- 모든 아이콘 버튼에 기능 중심 접근성 라벨을 제공한다.
- 화면 제목 → 상태 → 내용 → 주요 행동 순으로 읽힌다.
- 바텀시트가 열리면 첫 제목으로 초점을 이동하고 닫히면 호출 요소로 돌아간다.
- 상태 변경은 화면 읽기에 한 번만 안내한다.
- 큰 글자에서 단어 단위 줄바꿈이 공간을 과도하게 차지하면 한국어 글자 단위 줄바꿈을 검토한다.
- 오른쪽 화살표처럼 의미 없는 장식 아이콘은 읽지 않는다.
- 입력 오류는 필드와 요약 영역에서 모두 찾을 수 있게 한다.
- 터치 영역은 최소 48dp, 인접 위험 행동은 충분히 분리한다.
- 색각 이상에서도 라벨과 아이콘으로 상태를 구분한다.

## 12. 다크모드

- 1차 앱에서 토큰 구조는 지원하되 출시 기본은 라이트 모드다.
- 2차에서 OS 설정 연동을 제공한다.
- 단순 색상 반전이 아니라 표면 계층과 상태 대비를 다시 검증한다.
- 영수증 원본, QR 카메라, 차트는 주변 UI와 별도로 대비를 확인한다.
- 순수 검정 대형 배경보다 `#101214` 계열을 사용한다.

## 13. 반응형·기기 대응

### 모바일

- 기준 폭: 360~430dp
- 최소 검증: 320dp
- 폴드 내부 화면과 큰 글자는 2열을 1열로 전환한다.

### 태블릿

- 개인 모바일 앱을 단순 확대하지 않는다.
- 600dp 이상에서는 목록+상세 2열을 승인함과 영수증 검토에 사용할 수 있다.
- 공용 키오스크 앱과 내비게이션·인증 흐름을 섞지 않는다.

### 키보드·안전영역

- 하단 CTA는 키보드 위로 이동하되 입력 내용을 가리지 않는다.
- iOS Dynamic Island, 홈 인디케이터, Android 제스처 영역을 반영한다.
- 내부 스크롤을 중첩하지 않는다.

## 15. 디자인 QA 체크리스트

### 화면

- 첫 3초 안에 현재 상태와 주요 행동을 찾을 수 있는가?
- 한 화면에 primary CTA가 두 개 이상 경쟁하지 않는가?
- 카드가 아닌 행이나 섹션으로 묶을 수 있는 정보를 카드화하지 않았는가?
- 시간·금액·상태의 기준일과 기준 시각이 있는가?
- 빈 값, 긴 이름, 큰 금액, 다중 역할을 검증했는가?

### 상태

- 로딩, 빈 상태, 오류, 권한 변경, 오프라인, 오래된 데이터가 있는가?
- 성공 토스트만 보여주고 실제 원본을 갱신하지 않는 문제가 없는가?
- 중복 탭과 오래 열린 화면의 충돌을 처리하는가?
- 수집 실패를 0이나 정상으로 표시하지 않는가?

### 접근성

- 200% 글자 크기에서 행동이 유지되는가?
- VoiceOver/TalkBack 읽기 순서가 자연스러운가?
- 모든 터치 대상이 48dp 이상인가?
- 색 없이 상태가 구분되는가?
- 동작 줄이기와 다크모드에서 의미가 유지되는가?

### 문구

- 사용자 탓으로 단정하지 않는가?
- 기술 코드가 노출되지 않는가?
- 다음 행동이 구체적인가?
- 민감정보가 푸시·잠금화면에 노출되지 않는가?

## 19. 최종 원칙

TimeFit이 토스처럼 보여야 하는 것이 목표가 아니다. 사용자가 설명서를 읽지 않고도 현재 상태를 이해하고, 실수 없이 다음 행동을 끝내며, 결과를 신뢰할 수 있는 제품이 목표다.

따라서 디자인 검토는 `예쁜가`보다 다음 질문을 먼저 사용한다.

1. 사용자가 지금 상태를 한 문장으로 이해할 수 있는가?
2. 해야 할 행동이 하나로 보이는가?
3. 결과와 근거가 연결되어 있는가?
4. 오류와 권한 차이가 사용자 언어로 설명되는가?
5. 큰 글자·다크모드·화면 읽기에서도 같은 경험인가?
