# TimeFit 모바일 앱 2차 기능 및 사용자별 기획·설계

작성일: 2026-09-30  
문서 상태: 2차 구현 기준안 v1.0  
선행 문서: `128-mobile-app-product-planning-design-2026-09-30.md`  
대상: 1차 모바일 MVP 출시·안정화 이후 P1 고도화

## 1. 결론

2차 버전은 1차 앱의 조회·신청·승인 기능을 `협업이 끝까지 완료되는 운영 흐름`으로 확장한다.

핵심은 다음 세 가지다.

1. 직원의 근무 가능시간과 교대 요청이 매니저의 스케줄 조정, 변경 공지, 직원 확인까지 연결된다.
2. 영수증 OCR 오류와 관리자 수정 요청이 직원 재제출, 관리자 승인, 지출 원장 반영까지 한 상태로 이어진다.
3. 급여명세의 금액이 출퇴근·휴가·수당 근거와 연결되어 직원 문의와 관리자 재확인 비용을 줄인다.

2차에서도 급여 마감, 월간 스케줄 대량 편집, 카드사 연결, 회계 결산은 관리자 웹에 남긴다. 모바일은 즉시성이 높은 입력·확인·승인에 집중한다.

## 2. 2차 출시 목표

### 제품 목표

- 메신저로 처리하던 대타·교대·가능시간 수집을 앱 안의 추적 가능한 요청으로 전환한다.
- 매니저가 PC 없이도 하루 운영에 필요한 단일 스케줄 변경과 승인 처리를 완료한다.
- 직원이 영수증과 급여 결과의 수정 근거를 스스로 이해하고 대응한다.
- 사업주가 숫자 전체를 모바일에 복제하지 않고 긴급한 운영 상태만 판단한다.
- 권한을 역할 이름 하나가 아니라 기능과 담당 범위로 세분화한다.

### 출시 전제

2차 개발은 다음 1차 지표를 만족한 뒤 시작한다.

| 지표 | 진입 기준 |
|---|---:|
| QR 출퇴근 성공률 | 98% 이상 |
| 푸시 딥링크 정상 도착률 | 99% 이상 |
| 앱 비정상 종료 없는 세션 | 99.7% 이상 |
| 휴가 신청 완료율 | 90% 이상 |
| 사업장·역할 데이터 혼선 | 0건 |

기준 미달 시 2차 기능을 동시에 늘리지 않고 해당 1차 흐름을 먼저 안정화한다.

## 3. 2차 범위

| F2-02 | 교대·대타 요청 | 직원, 매니저 | 구두 합의와 승인 누락 |

| F2-08 | 급여명세 근거·전월 비교 | 직원, 총관리자 | 급여 문의의 원인 추적 어려움 |
| F2-09 | 사업장 공지·읽음 확인 | 매니저, 직원 | 운영 공지의 전달 여부 불명 |
| F2-10 | 다음 근무 위젯 | 직원 | 앱을 열어야 일정 확인 가능 |

### 3.2 조건부 기능

- 고객 리뷰·컴플레인 긴급 알림과 담당자 지정
- 카드 수집 실패·재인증 필요 알림
- 매출·지출·인건비의 제한된 사업주 요약

조건부 기능은 권한 모델, 데이터 완결성, 모바일 조치 가능성이 확인된 사업장에만 기능 플래그로 제공한다.

### 3.3 제외

- AI 자동 스케줄 확정
- 직원 간 자유 채팅
- GPS 상시 추적
- 모바일 급여 계산·마감·수정
- 모바일 월 결산·법인카드 연결
- 모든 관리자 웹 화면의 모바일 복제

## 4. 사용자 체계

2차 앱은 데이터베이스의 기본 역할과 실제 업무 페르소나를 구분한다.

| 기본 역할 | 앱 페르소나 | 설명 |
|---|---|---|
| `employee` | 시급제 직원 | 교대 근무, 출퇴근, 대타·휴가 요청이 잦음 |
| `employee` | 월급제 직원 | 고정 일정, 근태·급여 근거 확인 비중이 높음 |
| `manager` | 현장 매니저 | 당일 인력 운영, 스케줄 조정, 1차 승인 담당 |
| `manager` + 세부 권한 | 증빙 담당자 | 담당 부서 영수증 검토와 수정 요청 담당 |
| `owner` | 총관리자·사업주 | 권한, 예외, 급여·재무의 최종 책임자 |
| 별도 제한 계정 | 회계 담당자 | 증빙·결산 조회 중심, 직원 운영 정보는 최소 접근 |

한 사용자가 여러 페르소나에 해당할 수 있다. 앱은 계정을 여러 개 만들지 않고 `사업장 + 활성 역할 + 세부 권한`으로 화면을 구성한다.

## 5. 사용자별 기획

### 5.1 시급제 직원

#### 해결할 일

- 다음 근무와 변경 여부를 빠르게 확인한다.
- 근무 가능한 시간과 희망 휴무를 마감 전에 제출한다.
- 근무가 어려울 때 대타를 찾고 매니저 승인을 받는다.
- 실제 근무시간과 급여 반영 시간을 대조한다.
- 개인카드·법인카드 영수증을 수정 요청까지 포함해 끝낸다.

#### 홈 우선순위

1. 지금 출근·퇴근할 행동
2. 확인하지 않은 스케줄 변경
3. 응답 기한이 가까운 교대·대타 제안
4. 수정 요청된 영수증·근태
5. 다음 근무와 주간 예상 시간

#### 전용 빠른 행동

- 근무 가능시간 제출
- 교대 요청
- 대타 지원
- 영수증 재제출

#### 성공 기준

- 직원이 교대 요청 상태를 관리자에게 묻지 않고 앱에서 이해한다.
- 변경된 근무를 열고 확인하는 데 15초를 넘지 않는다.
- 급여명세에서 본인의 근무시간 산정 근거까지 3회 탭 이내에 도달한다.

### 5.2 월급제 직원

#### 해결할 일

- 고정 일정에서 예외적으로 바뀐 근무와 휴가만 확인한다.
- 누락 출퇴근과 연장·야간 근무 반영 여부를 확인한다.
- 급여명세의 수당·공제 변화 이유를 확인한다.

#### 홈 차이

- 근무 가능시간 카드는 기본으로 노출하지 않는다.
- `이번 달 근태 예외`, `공개된 급여명세`, `확인할 공지`를 우선한다.
- 교대 기능은 조직에서 허용한 경우에만 표시한다.

#### 성공 기준

- 전월 대비 금액 변화가 있을 때 근거 항목을 이해할 수 있다.
- 누락 근태에서 수정 요청까지 상세 화면을 이탈하지 않고 완료한다.

### 5.3 현장 매니저

#### 해결할 일

- 오늘 인원 부족과 미출근을 즉시 파악한다.
- 직원의 가능시간을 보고 단일 근무를 추가·수정한다.
- 교대 당사자, 근무 자격, 중복 일정, 총 근무시간을 검토한다.
- 휴가·근태·교대 요청을 우선순위대로 처리한다.
- 변경된 근무를 게시하고 직원 확인 여부를 추적한다.

#### 하단 내비게이션

```text
홈 / 직원 현황 / 스케줄 / 승인 / 전체
```

#### 홈 우선순위

1. 오늘 인력 부족·미출근·퇴근 누락
2. 오늘/내일 일정에 영향을 주는 승인 요청
3. 응답하지 않은 스케줄 변경 직원
4. 영수증·일반 승인
5. 주간 인원 요약

#### 모바일에서 허용

- 하루 한 직원의 근무 생성·수정·취소
- 휴게시간과 근무 유형 변경
- 교대 승인·반려
- 휴가·근태 수정 승인·반려
- 담당 직원 대상 공지 발행

#### 웹으로 이동

- 여러 직원 일괄 배정
- 반복 일정 생성
- 월간 템플릿 편집
- 급여 정책·계약 변경
- 민감 재무 처리

#### 성공 기준

- 긴급 단일 스케줄 변경을 1분 안에 게시한다.
- 승인 상세 한 화면에서 결정에 필요한 근거를 확인한다.
- 권한 밖의 직원·급여·재무 요약은 건수조차 보이지 않는다.

### 5.4 증빙 담당자

#### 해결할 일

- 담당 부서의 수정 필요 영수증을 먼저 본다.
- 원본과 OCR 결과를 비교해 단순 건을 빠르게 승인한다.
- 직원에게 어떤 값을 고쳐야 하는지 구체적으로 요청한다.

#### 화면 원칙

- `결산 차단 → OCR 실패 → 고액 불일치 → 장기 대기 → 고신뢰` 순으로 정렬한다.
- 모바일은 한 건 검토에 최적화하고 대량 확정은 웹에 남긴다.
- 원본 확대, 핵심 추출값, 카드 후보, 수정 이력을 탭으로 분리하지 않고 한 흐름으로 제공한다.

#### 성공 기준

- 고신뢰 단순 건 검토 중앙시간 30초 이내
- 수정 요청 사유의 90% 이상이 미리 정의된 필드와 사유로 구조화됨
- 담당 범위 밖의 부서 영수증과 금액이 노출되지 않음

### 5.5 총관리자·사업주

#### 해결할 일

- 담당자가 처리하지 못한 긴급 예외만 확인한다.
- 승인 권한과 기간을 다른 관리자에게 위임한다.
- 급여·증빙·운영 마감에 영향을 주는 항목을 판단한다.
- 재무 상세가 아닌 신뢰 가능한 제한 요약을 본다.

#### 홈 우선순위

1. 금액 또는 영업에 직접 영향을 주는 긴급 항목
2. 승인 위임 실패·기한 초과
3. 급여 마감 전 미해결 근태
4. 결산 차단 증빙
5. 데이터 최신성이 확인된 경영 요약

#### 모바일 행동 범위

- 최종 승인·반려
- 승인 담당자·기간 위임
- 긴급 공지
- 웹 상세 화면 딥링크
- 제한된 매출·지출·예상 인건비·잠정 순익 조회

경영 요약은 같은 기간, 같은 수집 상태, 같은 권한을 만족할 때만 노출한다. 수집 실패를 0원으로 표시하지 않는다.

### 5.6 회계 담당자

#### 해결할 일

- 결산을 막는 미증빙·불일치 항목을 확인한다.
- 원본, 카드 내역, 수정 이력, 확정 상태를 추적한다.
- 직원 운영 정보나 급여 개인 상세에 불필요하게 접근하지 않는다.

#### 앱 범위

- 결산 차단 알림
- 증빙 상세 조회
- 수정 요청 또는 검토 메모
- 웹 지출 원장·결산 화면 이동

직원 현황, 스케줄, 휴가 사유, 개인 급여는 기본적으로 숨긴다.

## 6. 기능 상세 설계

### 6.1 F2-01 근무 가능시간·희망 휴무

#### 흐름

```text
매니저가 제출 기간 생성
→ 직원에게 알림
→ 직원이 요일별 가능시간·불가시간·희망 휴무 입력
→ 제출 전 예상 시간 요약
→ 제출
→ 매니저가 미제출·충돌 확인
→ 스케줄 작성 참고
```

#### 입력 모델

- 대상 기간
- 요일별 가능 시작·종료
- 종일 불가
- 희망 휴무
- 최대 희망 근무시간
- 선택 메모
- 제출 버전과 제출 시각

#### 규칙

- 가능시간은 근무 확정이 아니라 직원의 희망 정보다.
- 제출 마감 뒤 수정은 매니저 정책에 따라 재요청한다.
- 매니저가 가능시간 밖 근무를 배정하면 경고하되 저장 가능 여부는 조직 정책으로 결정한다.
- 건강, 종교, 가족 사유 등 민감한 불가 사유 입력을 요구하지 않는다.

#### 수용 기준

- 직원은 기존 제출 내용을 복사해 다음 기간을 작성할 수 있다.
- 매니저는 미제출자와 충돌 근무를 구분해 본다.
- 다른 직원의 가능시간은 일반 직원에게 공개하지 않는다.

### 6.2 F2-02 교대·대타 요청

#### 요청 종류

- 교대: 직원 A와 B의 확정 근무를 서로 바꿈
- 대타 요청: 직원 A의 근무를 수행할 후보를 찾음
- 근무 양도: 지정 직원 B에게 근무를 넘김

#### 상태 모델

```text
draft
→ open
→ candidate_accepted
→ manager_review
→ approved
→ applied

분기: rejected / cancelled / expired / apply_failed
```

#### 기본 흐름

```text
직원 A가 근무 상세에서 요청
→ 대상 또는 공개 범위 선택
→ 후보 직원이 수락
→ 서버가 자격·중복·휴식·주간시간 검증
→ 매니저 승인
→ 하나의 트랜잭션으로 스케줄 변경
→ 양 당사자에게 새 일정 공지
→ 두 직원이 변경 확인
```

#### 검증

- 같은 사업장과 허용된 부서/직무
- 겹치는 근무·휴가 없음
- 최소 휴식시간과 최대 주간시간
- 필요한 자격·직무 충족
- 마감시간 이전 요청
- 원본 스케줄 버전이 요청 생성 후 바뀌지 않음

#### 원칙

- 후보 수락만으로 스케줄을 바꾸지 않는다.
- 승인과 두 스케줄 변경, 이력 저장은 하나의 트랜잭션으로 처리한다.
- 공개 대타 요청에서 직원 전화번호와 휴가 사유를 노출하지 않는다.
- 야간 알림은 다음 날로 지연하되 당일 근무 영향 요청은 예외로 한다.

### 6.3 F2-03 모바일 단일 스케줄 편집

#### 화면

- 날짜와 직원
- 근무지
- 근무 유형
- 시작·종료 시각
- 휴게시간
- 변경 사유
- 직원 가능시간·휴가·중복 충돌
- `초안 저장`과 `게시` 분리

#### 게시 규칙

- 게시 전 변경 전·후를 비교한다.
- 과거 일정은 별도의 근태 수정 흐름으로 안내한다.
- 게시 시 `schedule_version`을 증가시키고 대상 직원 알림을 생성한다.
- 동일 버전을 다시 게시해 중복 알림을 만들지 않는다.
- 이미 다른 관리자가 수정한 일정은 최신 버전을 다시 확인한다.

#### 제한

- 반복 일정, 복수 직원, 월간 복사 기능은 웹에서만 제공한다.
- 매니저는 담당 사업장·직원 범위만 수정한다.
- 임박한 일정 변경에는 직원 확인 필요 배지를 자동 설정한다.

### 6.4 F2-04 스케줄 변경 확인

- 변경 알림에는 날짜, 기존 시간, 새 시간, 근무지, 변경자를 표시한다.
- 직원은 `확인했어요` 또는 `근무가 어려워요`를 선택한다.
- 확인은 변경 동의나 근로조건 변경 계약으로 간주하지 않는다.
- `근무가 어려워요`는 교대 요청 또는 매니저 문의로 연결한다.
- 매니저는 읽음, 확인, 응답 필요, 알림 실패를 구분한다.
- 새 버전이 게시되면 이전 버전의 미확인 상태는 종료하고 최신 버전만 확인 대상으로 유지한다.

### 6.5 F2-05 통합 승인함·위임

#### 작업 종류

- 휴가
- 근태 수정
- 교대·대타
- 스케줄 예외
- 영수증 검토
- 향후 운영 피드백 담당 지정

#### 정렬 점수

우선순위는 숨겨진 AI 점수가 아니라 설명 가능한 규칙을 사용한다.

1. 오늘/내일 근무 영향
2. 급여·결산 마감 차단
3. 금액 영향
4. 대기 시간
5. 일반 요청

각 행에는 `왜 먼저 표시됐는지`를 문장으로 보여준다.

#### 승인 위임

- 위임자, 수임자, 조직·사업장, 기능, 시작·종료 시각을 저장한다.
- 위임 가능 기능은 위임자가 원래 가진 권한을 넘을 수 없다.
- 급여·재무 권한은 일반 운영 승인과 분리한다.
- 위임 생성·수정·해제와 위임 상태에서 한 결정은 감사 로그에 남긴다.
- 마지막 총관리자 권한은 위임으로 이전되지 않는다.

### 6.6 F2-06 영수증 OCR 확인·재제출

#### 직원 화면

- 원본 이미지
- 사용처, 거래일시, 총금액
- 공급가액·부가세
- 카드 끝 4자리
- 지출 목적
- 부서·섹션
- 잘못 읽힌 품목과 합계 경고

#### 수정 규칙

- OCR 원문은 수정하지 않고 정규화 값과 사용자 수정값을 분리한다.
- 날짜·금액 변경 시 카드 후보를 다시 계산한다.
- 관리자 확정 후에는 직원이 직접 수정하지 못하고 변경 요청을 보낸다.
- 수정 요청은 대상 필드, 사유, 관리자 설명, 기한을 포함한다.
- 재제출은 새 문서를 만들지 않고 같은 증빙의 버전을 증가시킨다.

#### 수용 기준

- 직원이 수정 요청된 필드로 바로 이동한다.
- 합계 검증을 통과하지 못한 품목 데이터는 지출 분석에 반영되지 않는다.
- 카드 내역과 영수증이 연결돼도 지출은 한 번만 합산된다.

### 6.7 F2-07 모바일 영수증 빠른 검토

#### 상세 구성

1. 검토 이유와 결산 영향
2. 원본 이미지 확대
3. OCR·사용자 수정값
4. 카드 후보와 점수 근거
5. 이력
6. 하단 고정 행동

#### 행동

- 승인
- 직원에게 수정 요청
- 별도 지출로 검토 요청
- 제외 요청
- 웹 상세 열기

`확정`과 `승인`의 의미가 다를 경우 모바일 문구를 명확히 분리한다. 증빙 승인만으로 회계 지출을 최종 확정하지 않는 조직에서는 `증빙 승인`이라고 표시한다.

### 6.8 F2-08 급여명세 근거·전월 비교

#### 정보 구조

```text
실지급액
├─ 지급: 기본급 / 연장 / 야간 / 휴일 / 기타 수당
├─ 공제: 세금 / 보험 / 기타 공제
├─ 근무 근거: 승인 근무시간 / 유급휴가 / 수정 반영
└─ 전월 변화: 금액 차이 + 원인 항목
```

#### 원칙

- 전월 계약·근무조건이 달라 직접 비교할 수 없으면 비교 불가 이유를 표시한다.
- 증가·감소를 좋음·나쁨 색상으로 자동 해석하지 않는다.
- 직원은 급여명세에서 해당 근태 일자로 이동할 수 있다.
- 급여 문의는 자유 채팅 대신 유형, 대상 항목, 설명을 포함한 구조화 요청으로 시작한다.
- 문의가 급여 확정 데이터를 자동 변경하지 않는다.

### 6.9 F2-09 사업장 공지

#### 기능

- 대상: 전체, 사업장, 부서, 개별 직원
- 중요도: 일반, 확인 필요, 긴급
- 게시 시작·종료
- 첨부 또는 링크
- 읽음·확인 상태
- 예약 게시

#### 규칙

- 일반 공지는 읽음, 중요한 정책·스케줄 공지는 명시적 확인을 사용한다.
- 확인 버튼이 법적 동의를 의미하는 문서에는 별도의 전자서명 절차를 사용한다.
- 급여·휴가·징계 등 개인 정보는 공지로 발송하지 않는다.
- 수정된 공지는 버전과 변경 내용을 표시하고 필요 시 다시 확인받는다.

### 6.10 F2-10 다음 근무 위젯

- 다음 근무 날짜·시간·근무지만 표시한다.
- 급여, 휴가 사유, 직원명 등 민감정보는 표시하지 않는다.
- 일정이 변경되면 위젯을 즉시 갱신한다.
- 로그아웃·퇴사·세션 폐기 시 위젯 정보를 삭제한다.
- 위젯에서 출퇴근을 바로 확정하지 않고 앱의 인증된 QR 흐름을 연다.

## 7. 사용자 간 핵심 연결 시나리오

### S2-01 가능시간에서 스케줄 게시까지

```text
매니저: 제출 기간 생성
→ 직원: 가능시간 제출
→ 매니저: 충돌 확인·스케줄 작성
→ 매니저: 게시
→ 직원: 변경 확인
→ 미확인 직원: 재알림
```

완료 기준은 스케줄 저장이 아니라 대상 직원이 최신 게시 버전을 확인하거나 매니저가 미확인 상태를 인지한 시점이다.

### S2-02 교대 요청 완료

```text
직원 A: 교대 요청
→ 직원 B: 수락
→ 시스템: 충돌 검증
→ 매니저: 승인
→ 시스템: 두 스케줄 동시 변경
→ A·B: 새 일정 확인
```

어느 단계에서든 원본 일정이 바뀌면 요청을 자동 적용하지 않고 재검토 상태로 전환한다.

### S2-03 영수증 수정 완료

```text
직원: 영수증 제출
→ 시스템: OCR·카드 후보
→ 증빙 담당자: 금액 수정 요청
→ 직원: 원본/값 수정·재제출
→ 시스템: 매칭 재계산
→ 담당자: 증빙 승인
→ 웹 결산: 지출 확정
```

### S2-04 급여 문의 해결

```text
직원: 급여명세 전월 차이 확인
→ 근무 근거 상세
→ 누락 의심 일자 선택
→ 급여 문의 생성
→ 총관리자: 원본 근태·급여 산식 검토
→ 답변 또는 정정 절차 시작
```

급여 문의와 근태 수정 요청을 중복 생성하지 않도록 관련 요청을 연결한다.

| 가능시간 제출 시작 | 대상 직원 | 기간 게시 | 입력 화면 |
| 가능시간 마감 임박 | 미제출 직원 | 24시간 전 | 입력 화면 |
| 대타 요청 | 적격 후보 | 요청 생성 | 요청 상세 |
| 후보 수락 | 요청자·매니저 | 수락 즉시 | 검토 상세 |
| 교대 승인·반려 | 당사자 | 결정 즉시 | 결과 상세 |
| 스케줄 변경 게시 | 대상 직원 | 게시 즉시 | 변경 비교 |
| 스케줄 미확인 | 직원·매니저 | 정책 시간 후 | 확인 현황 |
| 영수증 수정 요청 | 제출자 | 요청 즉시 | 해당 필드 |
| 급여 문의 답변 | 직원 | 답변 등록 | 문의 상세 |
| 중요 공지 | 대상자 | 게시 시각 | 공지 상세 |

중복 방지 키는 `event_type + entity_id + entity_version + recipient_id`로 구성한다.

## 13. 화면·상태 공통 규칙

- 목록으로 돌아가면 필터, 스크롤, 선택 사업장을 복원한다.
- 승인 후 행을 무조건 제거하지 않고 결과 상태를 짧게 보여준 뒤 갱신한다.
- 마지막 정상값과 갱신 중 상태를 함께 표시한다.
- 권한이 회수된 화면은 저장 전에 다시 검증하고 입력값을 안전하게 복사할 수 있게 한다.
- 삭제보다 취소·폐기 상태를 사용해 이력을 보존한다.
- 같은 요청을 두 관리자가 열면 먼저 처리된 결과를 최신 상태로 보여준다.
- 마감된 급여·결산에 영향을 주는 변경은 즉시 반영하지 않고 재검토 업무를 만든다.

## 17. 출시 게이트

### 기능

- 가능시간, 교대, 스케줄 게시가 하나의 최신 버전으로 연결된다.
- 교대 승인과 스케줄 변경이 트랜잭션으로 처리된다.
- 영수증 수정·재제출 이력이 원본과 연결된다.
- 급여명세의 근무 근거가 마감된 급여 데이터와 일치한다.

### 권한

- 역할이 아닌 세부 권한·범위·기간이 API와 RLS에서 적용된다.
- 위임받은 사용자가 위임자보다 넓은 권한을 행사할 수 없다.
- 재무·급여 권한이 없는 매니저에게 요약 건수나 금액도 노출되지 않는다.

### 정합성

- 중복 탭·재시도에도 요청·승인·게시가 한 번만 반영된다.
- 오래 열린 화면이 최신 스케줄·영수증·승인을 덮어쓰지 않는다.
- 스케줄 변경, 근태, 급여 근거의 날짜·시간대가 사업장 기준과 일치한다.

### 사용성

- 직원과 매니저의 핵심 UAT가 대표 iOS·Android 실기기에서 통과한다.
- 320px 폭과 시스템 글자 200%에서 핵심 행동이 잘리지 않는다.
- 푸시에서 정확한 사업장·역할·버전의 상세 화면으로 이동한다.

## 19. 첫 구현 단위

2차의 첫 개발 단위는 다음 수직 흐름으로 한다.

```text
직원 A가 대타 요청
→ 직원 B가 수락
→ 매니저가 충돌 근거 확인 후 승인
→ 두 스케줄을 트랜잭션으로 변경
→ A·B에게 변경 알림
→ 두 직원이 최신 버전을 확인
```

이 흐름은 2차에서 필요한 세부 권한, 상태 전이, 낙관적 잠금, 승인, 감사 로그, 알림, 스케줄 버전 확인을 모두 포함한다. 이 기반을 완성한 뒤 가능시간 수집, 모바일 단일 편집, 공지 확인을 같은 구조 위에 확장한다.
