# TimeFit 모바일 앱 기획·설계

작성일: 2026-09-30  
문서 상태: 구현 기준안 v1.0  
대상: iOS·Android 직원/매니저 앱  
연계 제품: 관리자 웹, TimeFit 태블릿 키오스크, Supabase/API

## 1. 결론

TimeFit 모바일 앱은 관리자 웹을 작은 화면에 옮기는 제품이 아니다. 직원과 현장 매니저가 이동 중에도 `오늘의 근무 확인 → 출퇴근 → 요청·승인 → 증빙 제출`을 짧게 끝내는 실행 도구로 만든다.

제품군은 다음처럼 역할을 분리한다.

| 제품 | 주 사용자 | 해결할 일 | 원칙 |
|---|---|---|---|
| TimeFit 모바일 | 직원, 매니저, 필요 시 사업주 | 개인 업무와 긴급 현장 조치 | 30초 안에 주요 행동 완료 |
| TimeFit 관리자 웹 | 사업주, 관리자, 회계 담당 | 설정, 대량 편집, 급여·매출·지출 분석 | 넓은 화면과 고밀도 업무 |
| TimeFit 키오스크 | 매장 공용 태블릿 | 전화번호 기반 출퇴근·휴가 신청 | 로그인 없는 공용 기기 전용 |

하나의 모바일 앱에서 로그인한 사용자의 역할에 따라 홈과 권한을 바꾼다. 키오스크는 기기 토큰과 공용 화면을 사용하므로 모바일 앱에 합치지 않는다.

### 1차 출시 핵심 가치

1. 직원은 오늘 근무와 변동 사항을 놓치지 않는다.
2. 출퇴근 기록과 수정 요청의 상태를 본인이 확인한다.
3. 휴가 신청과 영수증 제출을 메신저 없이 완료한다.
4. 매니저는 지각·미출근·승인 대기를 모바일에서 즉시 처리한다.
5. 공개된 급여명세를 본인만 안전하게 확인한다.

## 2. 현재 플랫폼 기준과 설계 판단

### 2.1 재사용 가능한 현재 자산

- 관리자/직원 역할과 조직·사업장 멤버십
- 직원 홈, 내 스케줄, 출퇴근, 휴가, 영수증의 웹 사용자 흐름
- 직원·스케줄·근태·휴가·급여 데이터 모델
- QR 출퇴근, 태블릿 전화번호 출퇴근, 출퇴근 수정 요청
- 휴가 승인/반려와 연차 잔여 계산
- 급여 마감·공개 상태와 명세서 PDF 생성
- 영수증 화질 검사, OCR, 카드 매칭, 수정 요청 상태 모델
- 총관리자/서브 관리자/직원 권한 구분
- Supabase 인증·RLS·RPC 기반 운영 구조

### 2.2 현재 공백

- 저장소에는 모바일 앱 소스가 없고 관리자 웹과 공개 태블릿 APK만 존재한다.
- 직원 웹 메뉴에는 개인 급여명세 진입이 아직 일관되게 제공되지 않는다.
- 푸시 토큰, 알림함, 기기 세션, 딥링크에 대한 통합 모델이 없다.
- 모바일 네트워크 단절·백그라운드 업로드·카메라 권한 정책이 정의되지 않았다.
- 매니저 모바일 화면의 범위가 웹 권한 설계와 분리되어 있지 않다.

### 2.3 이번 설계의 결정

- 신규 앱은 Flutter로 개발한다. 기존 네이티브 태블릿 설계와 디자인 토큰, Supabase 연동 패턴, 오류 모델을 재사용하기 쉽다.
- 앱 하나에서 `employee`, `manager`, `owner` 역할을 지원한다.
- 역할이 여러 개인 사용자는 현재 사업장과 역할을 명시적으로 전환한다.
- 출퇴근의 기준 기록은 서버 시각이다. 단말 시각은 참고값으로만 저장한다.
- 오프라인 상태에서 출퇴근을 성공으로 가장하지 않는다. 연결 복구 후 사용자가 다시 확정한다.
- 영수증 원본은 로컬 암호화 임시 저장 후 백그라운드 재전송할 수 있다.
- 급여 마감, 급여 정책, 카드 연결, 회계 결산, 대량 스케줄 편집은 웹에 남긴다.

## 3. 사용자와 핵심 과업

| 사용자 | 가장 중요한 과업 | 앱에서 제공 | 웹에 유지 |
|---|---|---|---|
| 직원 | 출퇴근, 일정 확인, 휴가, 영수증, 급여명세 | 전체 제공 | 선택적 조회 |
| 서브 관리자 | 오늘 인력 상태, 근태·휴가 승인, 긴급 스케줄 확인 | 빠른 조회·승인·간단 수정 | 대량 편집·정책 설정 |
| 총관리자 | 이상 상황 확인, 주요 승인, 경영 요약 확인 | 요약·딥링크 | 급여 마감·권한·재무 상세 |
| 회계 담당 | 결산과 증빙 검토 | 알림·요약만 | 전체 업무 |

### 대표 사용 상황

- 직원: 출근길에 변경된 근무 시간을 확인한다.
- 직원: 매장 QR을 스캔해 출근하고 기록된 서버 시각을 확인한다.
- 직원: 잘못된 퇴근 시간을 선택해 수정 요청을 보낸다.
- 직원: 휴가 잔여일을 보고 신청한 뒤 승인 결과를 받는다.
- 직원: 결제 직후 영수증을 촬영해 30초 안에 제출한다.
- 직원: 급여 공개 알림을 누르고 생체 인증 후 명세를 본다.
- 매니저: 미출근 알림을 받고 해당 직원 상태를 확인한다.
- 매니저: 휴가·근태 수정 요청을 근거와 함께 승인하거나 반려한다.

## 4. 1차 출시 범위

### 4.1 P0 — 출시 필수

- 초대 수락, 로그인, 사업장 선택, 약관·권한 온보딩
- 역할별 홈과 오늘 근무 카드
- 개인 주간·월간 스케줄 조회와 변경 표시
- QR 출근·퇴근, 현재 근무 상태, 최근 기록
- 출퇴근 수정 요청과 처리 상태
- 휴가 잔여 조회, 신청, 취소, 승인·반려 상태
- 영수증 촬영·화질 검사·필수 맥락 입력·제출 상태
- 공개 급여명세 조회와 PDF 공유/저장 정책
- 앱 알림함과 푸시 딥링크
- 매니저용 오늘 직원 상태, 휴가·근태 수정 승인
- 다중 사업장 전환과 권한별 데이터 차단

### 4.2 P1 — 첫 고도화

- 스케줄 교대 요청과 직원 간 대타 제안
- 매니저의 단일 근무 생성·수정
- 영수증 OCR 결과 수정과 재제출
- 매니저의 영수증 수정 요청·빠른 승인
- 홈 위젯 또는 잠금 화면의 다음 근무 표시
- 공지 확인과 읽음 상태
- 급여 전월 비교와 근태 산정 근거 연결

### 4.3 P2 — 데이터 검증 후

- GPS/비콘 보조 인증
- 운영 인사이트와 사업주 경영 요약
- AI 기반 스케줄 제안
- 직원 간 채팅
- 복지·전자계약·교육 콘텐츠

### 4.4 명시적 제외

- 모바일 급여 마감·수정
- 모바일 카드사 연결과 결산 확정
- 복잡한 월간 스케줄 대량 편집
- 공용 키오스크 모드
- 연결이 없는 상태에서의 출퇴근 자동 확정

## 5. 정보 구조

### 5.1 직원 하단 내비게이션

```text
홈
├─ 오늘 근무
├─ 출퇴근 주 행동
├─ 변경·승인 알림
├─ 빠른 행동: 휴가 / 영수증 / 수정 요청
└─ 이번 주 요약

스케줄
├─ 주간
├─ 월간
└─ 근무 상세·변경 이력

출퇴근
├─ QR 출근·퇴근
├─ 오늘 기록
├─ 월간 기록
└─ 수정 요청

요청
├─ 휴가
├─ 근태 수정
├─ 영수증
└─ 향후 교대 요청

전체
├─ 급여명세
├─ 알림함
├─ 사업장·역할 전환
├─ 내 정보
├─ 권한·보안
└─ 고객지원
```

### 5.2 매니저 하단 내비게이션

```text
홈 / 직원 현황 / 스케줄 / 승인 / 전체
```

- `홈`: 오늘의 운영 결론과 가장 긴급한 행동
- `직원 현황`: 근무 중, 예정, 지각, 미출근, 퇴근 누락
- `스케줄`: 오늘·주간 조회 중심, 단일 수정은 P1
- `승인`: 휴가와 근태 수정 요청을 하나의 작업 큐로 통합
- `전체`: 영수증 검토, 공지, 사업장 전환, 웹 관리자 열기

### 5.3 다중 역할 처리

- 앱 진입 시 마지막으로 사용한 사업장과 역할을 복원한다.
- 헤더의 사업장명을 누르면 전환 시트를 연다.
- 역할 변경 시 홈과 하단 내비게이션을 즉시 교체한다.
- 처리 중인 입력이 있으면 전환 전 임시 저장 또는 폐기 확인을 제공한다.
- 직원 역할에서는 관리자 데이터 API를 호출하지 않는다. 메뉴 숨김만으로 권한을 처리하지 않는다.

## 6. 핵심 화면 설계

### 6.1 로그인·초대 수락

목표: 처음 받은 초대에서 2분 안에 첫 홈에 도착한다.

흐름:

```text
초대 링크 열기
→ 기존 계정 확인
→ 로그인 또는 간편 가입
→ 사업장·역할·초대자 확인
→ 초대 수락
→ 알림/카메라 권한 안내
→ 홈
```

규칙:

- 가입 전에 사업장명과 부여 역할을 보여준다.
- 초대 만료·취소·이미 수락을 서로 다른 상태로 안내한다.
- 알림과 카메라 권한은 사용 이유를 설명한 뒤 OS 팝업을 호출한다.
- 생체 인증은 로그인 완료 후 선택적으로 설정한다.

### 6.2 직원 홈

첫 화면은 `지금 무엇을 해야 하는가`에 답한다.

```text
09:00–18:00 · 버터블라 성수점
오늘은 오픈 근무예요
[QR 출근하기]

변경된 일정 1건 · 승인 결과 1건

[휴가 신청] [영수증 올리기] [근태 수정]

이번 주 24시간 30분
다음 근무: 수요일 12:00
```

상태 우선순위:

1. 현재 출근/퇴근이 필요한 상태
2. 오늘 스케줄 변경
3. 반려·수정 요청처럼 대응이 필요한 알림
4. 다음 근무와 주간 요약

스케줄이 없는 날에는 출근 버튼을 숨기지 않고 `예정된 근무가 없어요`와 `예외 출근 요청` 정책을 안내한다.

### 6.3 QR 출퇴근

흐름:

```text
홈의 출근 버튼
→ 카메라 열기
→ 사업장 QR 인식
→ 사업장·현재 상태 검증
→ 출근/퇴근 확인
→ 서버 저장
→ 기록 시각·근무지·다음 행동 표시
```

검증:

- 로그인 사용자와 직원 프로필 연결
- QR의 사업장, 만료, 서명 검증
- 현재 사업장 멤버십과 근무 가능 상태
- 동일 근무일 중복 출근·퇴근
- 스케줄 없는 근무의 사업장 정책
- 서버 시각과 기기 시각 차이 기록

결과 화면은 `출근이 기록됐어요 · 09:02`처럼 사실을 먼저 보여준다. 성공 후에는 홈과 기록 목록을 같은 서버 응답으로 갱신한다.

예외:

- 카메라 거부: 설정 열기와 관리자 수정 요청 제공
- QR 만료: 새 QR 요청 안내
- 네트워크 없음: 성공 처리하지 않고 재시도 제공
- 중복 요청: 기존 기록을 보여주고 추가 저장 금지
- 다른 사업장 QR: 현재 사업장 전환 가능 여부 안내

### 6.4 스케줄

- 기본은 7일 주간 목록이며 오늘로 스크롤한다.
- 월간 달력은 근무/휴무/휴가와 변경 표시만 요약한다.
- 상세에는 근무지, 시작·종료, 휴게, 근무 유형, 게시 시각, 변경 이력을 표시한다.
- 변경된 일정은 이전 값과 새 값을 비교하고 확인 여부를 기록한다.
- 미게시 초안은 직원에게 절대 노출하지 않는다.

### 6.5 출퇴근 기록·수정 요청

- 월간 상단에 총 근무, 연장, 야간, 휴일, 수정 대기를 구분한다.
- 일자 행에는 예정과 실제 기록을 함께 보여준다.
- 수정 요청은 원본을 보존하고 희망 시각·사유·첨부를 별도로 저장한다.
- 승인 전에는 급여 반영 전 상태임을 명시한다.
- 반려에는 관리자 사유와 재요청 행동을 제공한다.

### 6.6 휴가

상단 요약:

- 사용 가능
- 승인 대기
- 올해 사용

신청 흐름:

```text
휴가 유형
→ 날짜/시간
→ 잔여 및 스케줄 충돌 확인
→ 선택적 사유·첨부
→ 최종 요약
→ 신청 완료
```

규칙:

- 사용 가능 잔여와 승인 대기 예정 차감을 분리한다.
- 공휴일·정기휴일 제외 정책을 달력에 즉시 반영한다.
- 중복 신청과 승인된 휴가를 차단한다.
- 관리자 처리 전에는 직원이 취소할 수 있다.
- 반려 사유는 신청자 본인과 승인권자만 조회한다.

### 6.7 영수증 제출

첫 화면의 주 행동은 `영수증 촬영` 하나다.

```text
촬영/앨범 선택
→ 자르기·회전·화질 검사
→ 부서·섹션 / 결제수단 / 지출 목적 확인
→ 원본 업로드
→ OCR 처리
→ 핵심 추출값 확인
→ 제출
→ 처리 상태 추적
```

상태 표현:

- 임시 저장
- 업로드 중
- 분석 중
- 내 확인 필요
- 관리자 검토 중
- 수정 요청
- 승인 완료
- 제출 실패

업로드 실패 시 원본을 앱 전용 저장소에 암호화해 보관하고 연결 복구 후 재전송한다. 사용자가 로그아웃하거나 제출을 취소하면 임시 원본을 삭제한다.

### 6.8 급여명세

- 공개된 급여 실행만 표시한다.
- 목록에는 귀속월, 지급일, 실지급액, 공개 상태를 표시한다.
- 상세 진입 시 생체 인증 또는 기기 자격 증명을 선택적으로 재확인한다.
- 기본급, 수당, 공제, 근무시간 근거, 실지급액을 구분한다.
- PDF 저장·공유는 조직 정책에 따라 허용하며 민감정보 경고를 표시한다.
- 미공개 급여는 금액 대신 `관리자 검토 중`으로 표시한다.

### 6.9 매니저 홈·승인함

매니저 홈의 첫 문장 예시:

```text
오늘 1건을 먼저 확인해 주세요
지각 1명 · 미출근 0명 · 승인 대기 3건
```

승인함은 요청 유형별 탭보다 긴급도 기준의 단일 작업 큐를 기본으로 한다.

정렬:

1. 급여 마감을 막는 근태 수정
2. 오늘 또는 다음 근무에 영향을 주는 휴가
3. 오래 대기한 요청
4. 일반 확인

승인 상세에는 원본, 요청값, 스케줄, 충돌, 잔여, 신청 이력을 함께 보여준다. 스와이프만으로 승인하지 않고 명시적 버튼과 결과 피드백을 사용한다.

## 7. 알림 설계

### 7.1 알림 종류

| 이벤트 | 대상 | 기본 채널 | 딥링크 |
|---|---|---|---|
| 스케줄 게시·변경 | 직원 | 푸시+알림함 | 스케줄 상세 |
| 출근 임박·미출근 | 직원/매니저 | 푸시 | 오늘 근무/직원 상태 |
| 퇴근 누락 | 직원/매니저 | 푸시 | 해당 근태 기록 |
| 휴가 신청 | 승인권자 | 푸시+알림함 | 승인 상세 |
| 휴가 승인·반려 | 신청자 | 푸시+알림함 | 휴가 상세 |
| 근태 수정 결과 | 신청자 | 푸시+알림함 | 수정 요청 상세 |
| 영수증 수정 요청 | 제출자 | 푸시+알림함 | 영수증 상세 |
| 급여명세 공개 | 직원 | 푸시+알림함 | 급여명세 |

### 7.2 알림 원칙

- 알림 본문에 급여 금액, 휴가 사유, 전화번호 등 민감정보를 넣지 않는다.
- 동일 이벤트의 푸시·알림톡·이메일 발송은 하나의 이벤트 ID로 중복을 막는다.
- 읽음은 기기별이 아니라 사용자별로 동기화한다.
- 근무 시작 알림은 사용자별 끄기와 시간 조정을 제공한다.
- 야간 방해 금지 시간에는 긴급하지 않은 알림을 묶어 보낸다.
- 알림을 눌렀을 때 로그인·사업장·권한 검증 후 정확한 상세로 이동한다.

## 8. 상태 모델

### 8.1 출퇴근

```text
scheduled
→ checked_in
→ checked_out

예외: late / absent / missing_checkout / correction_pending / corrected
```

서버의 기존 상태와 화면 문구를 일대일 매핑하고 클라이언트가 임의 계산한 상태를 영구 저장하지 않는다.

### 8.2 휴가 요청

```text
draft → pending → approved
                ├→ rejected
                └→ cancelled
```

### 8.3 근태 수정 요청

```text
draft → pending → approved → applied
                └→ rejected
```

승인과 원본 반영을 분리해 트랜잭션 실패를 추적한다.

### 8.4 영수증

문서 처리 상태, 직원 제출 상태, 회계 확정 상태를 합치지 않는다.

```text
processing_status: uploaded / queued / processing / needs_submitter_review / ready_for_review / failed
review_status:     draft / submitted / change_requested / approved / rejected / withdrawn
expense_status:    draft / review_required / confirmed / excluded / adjusted
```

### 10.3 API 원칙

- 홈은 여러 화면 API를 연쇄 호출하지 않고 역할별 집계 응답 하나로 제공한다.
- 모든 생성 API는 클라이언트 생성 `idempotencyKey`를 받아 중복 탭·재시도를 방지한다.
- 목록은 커서 기반 페이지네이션을 사용한다.
- 날짜는 API에서 ISO 8601, 화면은 사업장 `Asia/Seoul` 기준으로 표시한다.
- 금액은 정수 원 또는 decimal 문자열로 전달하고 부동소수점 계산을 피한다.
- 앱 최소 지원 버전과 강제 업데이트 정책을 원격 설정으로 제공한다.

권장 엔드포인트/RPC:

GET  /mobile/leave/summary
POST /mobile/leave/requests
POST /mobile/receipt-uploads

현재 Supabase RPC를 유지할 경우에도 앱에서는 저장소 계층을 통해 호출해 함수명이 UI 코드에 퍼지지 않게 한다.

| 기능 | 오프라인 정책 |
|---|---|
| 홈·스케줄·급여명세 | 마지막 동기화 값 읽기 가능, 기준 시각 표시 |
| 출퇴근 | 성공 확정 금지, 연결 복구 후 재시도 |
| 휴가·근태 수정 | 임시 저장 가능, 전송은 사용자 확인 후 수행 |
| 영수증 | 암호화 임시 저장과 자동 재업로드 가능 |
| 승인 | 오프라인 처리 금지, 최신 상태 재조회 후 결정 |

오류 문구는 기술 코드 대신 다음 행동을 포함한다.

- 복구 가능: `연결이 불안정해요. 입력 내용은 저장됐으며 다시 보낼 수 있어요.`
- 최신 상태 충돌: `다른 기기에서 먼저 처리됐어요. 최신 내용을 불러왔어요.`
- 권한 변경: `이 사업장의 관리 권한이 변경됐어요.`
- 서버 지연: 요청 결과를 다시 조회하고 중복 생성하지 않는다.

## 13. 보안·개인정보

- 앱 시작과 사업장 전환마다 세션·멤버십·역할을 서버에서 확인한다.
- RLS는 조직과 직원 본인 조건을 강제한다.
- 출퇴근 QR은 서명, 사업장, 만료시각, nonce를 포함한다.
- 푸시 토큰 원문은 제한된 서버 영역에서만 관리하고 일반 로그에 남기지 않는다.
- 전화번호, 급여, 휴가 사유, 영수증 원본은 분석 로그와 오류 추적에 포함하지 않는다.
- 급여명세와 영수증 원본 URL은 짧은 만료시간의 서명 URL로 발급한다.
- 탈퇴·퇴사·기기 분실 시 해당 기기 세션과 푸시 토큰을 폐기한다.
- 스크린샷 차단은 급여·개인정보 화면에서 조직 정책으로 선택 가능하게 한다.
- 루팅/탈옥 기기는 경고하되 1차 출시에서 무조건 차단하지 않는다.
- 감사 로그에는 누가, 언제, 어느 조직에서, 어떤 원본을 어떤 값으로 변경했는지 기록한다.

## 17. 출시 게이트

### 기능

- 초대부터 홈까지 신규 사용자가 막힘없이 완료한다.
- 직원 P0 5대 흐름인 스케줄, 출퇴근, 휴가, 영수증, 급여명세가 운영 데이터로 연결된다.
- 매니저 승인 결과가 관리자 웹과 직원 앱에 같은 상태로 표시된다.
- 다중 사업장 사용자의 데이터가 섞이지 않는다.

### 보안

- 직원이 다른 직원의 근태·휴가·급여를 조회할 수 없다.
- 매니저가 권한 없는 급여·재무 API를 호출하면 서버에서 차단된다.
- 만료·폐기된 세션과 기기는 접근할 수 없다.
- 로그와 푸시에 민감정보가 포함되지 않는다.

### 품질

- 지원 OS의 대표 실기기에서 카메라·푸시·딥링크가 통과한다.
- 네트워크 전환, 앱 강제 종료, 백그라운드 복귀 후 중복 기록이 없다.
- 출퇴근과 승인 API는 반복 요청에도 한 번만 반영된다.
- 큰 글자, 화면 읽기, 색상 대비 핵심 시나리오가 통과한다.

### 운영

- 앱 버전별 오류율과 API 실패율을 확인할 수 있다.
- 최소 지원 버전과 점검 공지를 원격 제어할 수 있다.
- 분실 기기 세션 폐기와 사용자 문의 대응 절차가 준비되어 있다.

## 18. 구현 전 확정할 정책

아래는 제품 방향을 바꾸지 않는 범위의 운영 결정이며, 기본 권장값을 함께 제시한다.

| 항목 | 권장 기본값 |
|---|---|
| 첫 출시 대상 | 직원 + 현장 매니저 |
| 출퇴근 인증 | 로그인 사용자 + 매장 QR |
| 스케줄 없는 출근 | 기록은 보류하고 매니저 승인 요청 |
| 휴가 사유 | 선택 입력, 조직 정책으로 필수화 가능 |
| 급여명세 재인증 | 생체 인증 또는 기기 자격 증명 |
| 급여 PDF 공유 | 기본 허용, 민감정보 경고 표시 |
| 매니저 스케줄 편집 | 1차는 조회, P1에서 단일 수정 |
| 영수증 오프라인 | 암호화 임시 저장 후 자동 재전송 |
| 최소 OS | 파일럿 기기 분포 확인 후 확정 |
| 푸시 제공자 | FCM 중심, iOS는 APNs 연계 |

## 19. 첫 개발 단위

첫 구현 단위는 `초대 수락 → 직원 홈 → 오늘 근무 → QR 출근 완료`의 수직 흐름으로 한다.

이 단위에서 인증, 사업장 컨텍스트, 역할 권한, 서버 시각, QR 검증, 네트워크 오류, 분석 이벤트까지 실제 운영 구조로 완성한다. 이 기반을 먼저 안정화하면 스케줄·휴가·영수증·매니저 승인 기능이 같은 앱 구조와 보안 경계를 재사용할 수 있다.
